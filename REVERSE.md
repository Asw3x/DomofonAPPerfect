# Как восстанавливался API: реверс клиента домофона

Этот документ — про то, откуда взялся протокол, по которому работает приложение.
Сам клиент написан с нуля на Kotlin и Jetpack Compose, но серверная часть не моя и не
документирована: её пришлось восстанавливать из официального приложения.

## Зачем

У официального клиента не было нужного мне поведения: настраиваемая задержка закрытия окна
после открытия двери, нормальное масштабирование видео с камер и своя структура папок для
сортировки камер и дверей. Переписывать UI поверх чужого API оказалось проще, чем ждать.

## Инструменты

- `apktool` — распаковка, ресурсы и манифест 
- `jadx` — декомпиляция в читаемую Java/Kotlin
- перехват HTTPS-трафика на своём устройстве 

## Что вскрылось

Бэкенд разбит на три подсистемы, и это видно прямо по путям:

| Префикс | Назначение |
|---|---|
| `sso-api/` | авторизация |
| `client-api/` | ключи, двери, журнал звонков |
| `communication-api/` | сигнализация о состоянии звонка |

### Авторизация

```
POST sso-api/Authorization/Authorize
     { "phoneNumber": { "countryCode": <int>, "number": <long> } }

POST sso-api/Authorization/ConfirmAuthorization
     { "phoneNumber": {...}, "confirmCode": "<из SMS>", "deviceToken": "<FCM>" }
  -> { "token": "...", "refreshToken": "..." }
```

Два шага: телефон → код из SMS → пара токенов. `deviceToken` — токен FCM, по нему сервер
знает, куда слать пуш о входящем звонке.

Отдельная деталь, которая и определила архитектуру клиента: номер телефона передаётся
структурой `{countryCode, number}`, а не строкой. Пока я этого не воспроизвёл точно, сервер
отвечал ошибкой — и это типично для реверса: формат важнее эндпоинта.

### Ключи и двери

```
POST client-api/Key/GetPagedKeysByKeysType
     { "currentPage": 1, "perPage": 100, "keysType": "Active", "search": null }
```

Возвращает список объектов:

```kotlin
data class KeyResponse(
    val id: String,
    val name: String,
    val httpVideoUrl: String?,     // поток камеры по HTTP
    val webrtcVideoUrl: String?,   // он же через WebRTC
    val videoPreview: String?,
    val doorId: String
)
```

То есть у каждого ключа есть и идентификатор самого ключа, и идентификатор двери, и два разных
URL видеопотока. Отсюда и возможность сделать своё масштабирование и свою группировку: вся
нужная информация уже в ответе, официальный клиент просто показывает её по-своему.

### Открытие двери

```
POST client-api/Device/OpenRelayByKeyId    { "keyId": "<id>" }
POST client-api/Device/OpenRelayByDoorId   { "doorId": "<id>" }
```

Ответ — голый `Boolean`.

### Звонки

Входящий звонок приходит пушем через FCM, медиа — WebRTC/SIP, об окончании клиент сообщает сам:

```
POST communication-api/Call/NotifyCallEnded   { "callId": "<id>" }
```

## Клиент

Retrofit + `kotlinx.serialization`, слой данных отделён от UI
(`data/network` → `data/repository` → Compose-экраны), входящие звонки обрабатываются
`FloatingCallService` поверх других приложений, пуши — `MyFirebaseMessagingService`.

## Push-уведомления

Входящий звонок приходит через FCM, и чтобы клиент их получал, ему нужна конфигурация того
Firebase-проекта, которому эти пуши адресованы. Она извлечена из оригинального приложения —
иначе уведомления о звонке в домофон просто не доходят, а без них клиент бесполезен.

Если собираешь проект под себя, можно подставить `app/google-services.json` своего
Firebase-проекта: всё остальное — список ключей, камеры, открытие двери — работает и так,
не придут только пуши.

## Что здесь интересно с точки зрения безопасности

Я намеренно **не** превращал этот проект в поиск уязвимостей чужого сервиса и не тестировал
ничего за пределами собственного домофона и собственной учётной записи.

Но одно наблюдение из самого дизайна API стоит записать, потому что оно типовое:
операция открытия двери принимает **идентификатор объекта** (`keyId` / `doorId`) и возвращает
`Boolean`. В такой схеме вся авторизация обязана быть серверной — сервер должен проверять, что
дверь с этим идентификатором действительно принадлежит владельцу токена. Если проверка
выполняется только на клиенте (например, тем, что приложение показывает лишь свои ключи), то
перед нами классический IDOR — с той разницей, что объект доступа здесь не запись в базе,
а физическая дверь.

Проверять это на чужих дверях нельзя и не нужно: это не исследование, а проникновение.
Корректный путь, если такой вопрос возникает, — обратиться к вендору напрямую, а не
экспериментировать на подъездах соседей.
